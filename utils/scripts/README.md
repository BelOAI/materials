# Добавление, сборка и публикация материалов

Команды выполняются из корня репозитория. Сайт публикуется на [GitHub Pages](https://materials.beloai.by/).

## Что нужно для сборки

- Python 3.14, GNU Make и Bash 4 или новее.
- TeX Live с `pdflatex`, пакетами Beamer, TikZ, математическими пакетами и поддержкой русского языка.
- `pdfinfo` и `pdftoppm` из Poppler — для превью PDF.
- Jupyter и `nbconvert` — для HTML-версий ноутбуков. Без Jupyter доступно скачивание `.ipynb`.
- Node.js 24 LTS и npm — для интерфейса Lit.

В CI зависимости устанавливаются автоматически. На macOS системного Bash 3 недостаточно: установите современный Bash и убедитесь, что он доступен через `PATH`. Шрифты уже находятся в `utils/site/fonts/`; для их обновления служит `bash utils/scripts/vendor-fonts.sh`.

После клонирования установите зависимости интерфейса:

```bash
npm --prefix utils/site ci
```

## Добавить материал

1. Скопируйте шаблон нужного раздела: [лекции](../../course/lectures/README.md), [практики](../../course/practices/README.md) или [задания](../../course/assignments/README.md).
2. Заполните `meta.yaml`: название, дату, описание, `build: true`. Для задания добавьте `assignment_type`.
3. Обновите `main.tex` и содержимое либо укажите готовый PDF в поле `pdf`. Порядок фрагментов задают команды `\input` в `main.tex`.
4. При необходимости добавьте файлы в `materials/` и ссылки в `references`.
5. Назначьте материал неделе в `course/course.json`.
6. Соберите материал и сайт, проверьте результат в браузере.

Нумерация каждого раздела независима. Например, `course/lectures/02-topic` даёт подпись «Лекция 2». Папки `_template*` не публикуются.

Материал может содержать только ссылки или ноутбук: в таком случае `main.tex` не нужен. Сайт показывает запись, если есть хотя бы один собранный файл или внешняя ссылка.

## Метаданные: `meta.yaml`

Пример минимальной записи:

```yaml
title: "Название занятия"
date: "2026-10-10"
description: "Что изучим и какие задачи разберём."
build: true
```

| Поле | Назначение |
| --- | --- |
| `title` | Название материала |
| `subtitle` | Необязательный подзаголовок |
| `description` | Краткое описание для учеников |
| `date` | Дата занятия или выдачи задания, `YYYY-MM-DD` |
| `slot` | Время занятия: `1` — 11:25–12:50, `2` — 13:15–14:40; по умолчанию `1` |
| `time` | Произвольное время, например `10:30–12:00`; заменяет `slot` |
| `assignment_type` | Для заданий: `math` или `coding` |
| `build` | `false` отключает общую сборку и публикацию записи; по умолчанию `true` |
| `hidden` | `true` скрывает запись из каталога, сохраняя сборку файлов; по умолчанию `false` |
| `pdf` | Необязательный относительный путь к готовому основному PDF; имеет приоритет над `main.tex` |
| `lang` | Справочная отметка языка; язык LaTeX задаётся в `main.tex` |
| `materials` | Дополнительные файлы |
| `references` | Внешние ссылки |

Для задания время не подставляется автоматически: используйте `time`, если оно требуется. В общем каталоге новые даты идут первыми, задания первыми внутри даты, затем лекции и практики по времени от поздних к ранним. На странице недели материалы сгруппированы по виду и следуют порядку `course/course.json`.

Используется простой парсер, а не полный YAML: обычные поля и списки записей. Пишите описания одной строкой, без многострочных блоков и комментариев после значений.

### Готовый PDF вместо TeX

Для лекции, практики или задания создайте папку занятия и `meta.yaml`, положите PDF, например, в `materials/lecture.pdf`:

```yaml
title: "Название занятия"
date: "2026-10-10"
description: "Что изучим и разберём."
build: true
pdf: materials/lecture.pdf
```

Для домашнего задания также укажите `assignment_type: math` или `coding`. Выполните `make -f build/Makefile session DIR=course/lectures/02-topic`, затем `make -f build/Makefile site`. Файл станет основным PDF с превью первой страницы. В `materials` его повторно перечислять не нужно; другие PDF можно добавить туда как дополнительные файлы.

Путь должен быть относительным и оставаться внутри папки занятия, включая цель символической ссылки. Пробелы и кириллица допустимы. Файл проверяется утилитой `pdfinfo` из Poppler; отсутствующий, повреждённый или зашифрованный PDF вызывает ошибку без подмены TeX-версией. Имя `main.pdf` зарезервировано для результата TeX: используйте другое имя для исходного файла.

При наличии `pdf` обычная сборка не запускает TeX. Команда `make -f build/Makefile tex DIR=course/lectures/02-topic` отдельно создаёт локальный `main.pdf` и не заменяет опубликованный файл. Чтобы вернуться к TeX, удалите поле `pdf` и пересоберите занятие. Старые PDF, превью и дополнительные файлы удаляются при пересборке; общая сборка также удаляет результаты исключённых и удалённых занятий.

Исходные PDF коммитятся вместе с материалом. `make -f build/Makefile clean` сохраняет их, удаляя только результаты сборки и файлы LaTeX.

### Файлы

Пути задаются относительно папки материала:

```yaml
materials:
  - path: materials/notebook.ipynb
    label: Разбор задач
  - path: materials/data.csv
    label: Данные
```

`label` необязателен, но помогает различать несколько файлов. При совпадении подписей файлов к ним добавляются имена файлов. Сборка копирует файлы в `_site/materials/<раздел>/<папка>/`, без исходных вложенных папок. Поэтому имена файлов внутри одного материала должны различаться. Для `.ipynb` создаётся HTML без выполнения ячеек. Отсутствующие файлы пропускаются с предупреждением; ссылки на них не публикуются.

### Внешние ссылки

```yaml
references:
  - kind: contest
    url: https://new.contest.yandex.ru/contests/98758
    label: Задачи занятия
```

Замените URL на адрес своего контеста для учеников. Для `contest`, `kaggle`, `huggingface`, `colab` подписи по умолчанию — «Яндекс.Контест», «Kaggle», «Hugging Face», «Google Colab». Для произвольной ссылки укажите `label` и `url`. Используйте HTTP или HTTPS. Контесты показываются первыми, остальные ссылки — по подписи.

## Команды

```bash
make -f build/Makefile session DIR=course/lectures/02-topic  # PDF и дополнительные файлы одного занятия
make -f build/Makefile tex DIR=course/lectures/02-topic      # только локальная TeX-сборка, без публикации
make -f build/Makefile materials DIR=course/lectures/02-topic  # только дополнительные файлы
make -f build/Makefile handbooks                     # учебник и общая оболочка, без сборки занятий
make -f build/Makefile frontend                     # только CSS и JS интерфейса
make -f build/Makefile test                         # тесты генератора и проверки манифеста
make -f build/Makefile site                         # все материалы, превью, интерфейс и манифест
make -f build/Makefile clean                        # удалить результаты сборки и файлы LaTeX
```

`make -f build/Makefile` равнозначен `make -f build/Makefile site`. Команда `make -f build/Makefile session` обновляет PDF, превью и дополнительные файлы, но не обновляет каталог: после неё выполните `make -f build/Makefile site`. Ошибки LaTeX смотрите в `main.log` папки материала. Сборка подключает общие пакеты через `TEXINPUTS` и дважды запускает `pdflatex`.

Для локального просмотра:

```bash
python3 -m http.server 8000 --directory _site
```

Откройте <http://localhost:8000/>. Нужен HTTP-сервер: открытие `index.html` через `file://` не подходит для загрузки манифеста.

Для материала с PDF создаётся PNG-превью первой страницы. Если PDF нет, для первого доступного ноутбука из списка `materials` создаётся SVG с первыми непустыми ячейками кода, подсветкой синтаксиса и значком Python. Ячейки не выполняются; их сохранённые выводы не отображаются. Превью ноутбуков работают для лекций, практик и заданий. Название материала открывает PDF, HTML-версию ноутбука или `.ipynb` в этом порядке. Превью появляется при наведении или фокусе на компьютере; на телефоне оно отключено. Ноутбук без кода или повреждённый ноутбук остаётся без превью; ошибки чтения выводятся как предупреждения.

## Структура занятий: `course/course.json`

Неделя — учебный модуль; даты занятий не определяют её номер. Порядок недель задаёт массив `weeks`, порядок материалов внутри каждого раздела — массив `materials` недели:

```json
{
  "title": "Подготовка к BelOAI",
  "description": "Краткое описание подготовки.",
  "weeks": [
    {
      "slug": "intro-ml",
      "number": 1,
      "title": "Введение в машинное обучение",
      "description": "Темы этой недели.",
      "materials": ["lectures/01-intro-ml", "practices/01-numpy-pandas"]
    }
  ]
}
```

`slug` состоит из строчных латинских букв, цифр и одиночных дефисов между ними; это постоянная часть URL `/weeks/<slug>/`. Номера — уникальные неотрицательные целые числа. Название и описание обязательны для раздела подготовки и каждой недели. Идентификатор материала — путь его папки относительно `course/`: например, `lectures/02-topic`. Публичные идентификаторы и адреса файлов сохраняются при переносе исходников.

Все публичные материалы должны быть назначены ровно одной неделе, включая ещё не собранные. Неизвестные идентификаторы, повторы, одинаковые номера или slug останавливают генерацию. В ссылках структуры можно сохранять скрытые и отключённые материалы: в публикацию они не попадут. Недели без доступных ресурсов не выводятся; старые страницы недель удаляются при генерации.

Главная находится в корне сайта, общий каталог — `/materials/`. На GitHub Pages адреса учитывают префикс `/materials/` репозитория: например, общий каталог доступен по `/materials/materials/`. Файлы сохраняют прежние адреса.

## Как устроен сайт

`build-all.sh` вызывает `build-session.py`, который выбирает готовый PDF или TeX и публикует его. `build-materials.sh` копирует дополнительные файлы и запускает `material_preview.py`: тот создаёт превью первой страницы PDF либо кода первого доступного ноутбука. `generate-site.py` проверяет структуру занятий и публикует `materials.json`, статические страницы и шрифты; HTML формирует `course_site.py` по шаблону `utils/site/index.html`. esbuild собирает интерфейс из `utils/site/src/` в `_site/assets/`.

Манифест содержит `version: 2`, объект `course` и массив `materials`. Объект `course` повторяет структуру `course/course.json`, но содержит только опубликованные недели и доступные материалы. В записи находятся `id` (путь папки), `kind`, `number`, `title`, `subtitle`, `description`, `date`, `time`, списки `materials` и `references`. Для задания есть `assignment_type`; для доступных PDF и превью — `pdf` и `thumb`. Поле `thumb_href` задаёт переход по превью. Адреса файлов относительны корню сайта. Дополнительный файл содержит `label`, `download`, `open`, `is_notebook`; недоступный адрес обозначается пустой строкой. Внешняя ссылка содержит `kind`, `label`, `url`.

HTML содержит навигацию и все ресурсы без JavaScript. Lit загружает манифест для поиска и фильтров общего каталога; при ошибке загрузки статический список остаётся доступен. Поиск по названию, подзаголовку и описанию использует параметр `q`; фильтры поддерживают `#lectures`, `#practices`, `#assignments`. Старые hash-ссылки с главной переводят в каталог. Назад/вперёд восстанавливают поиск и фильтр. CSS и JS поставляются локально, без CDN.

## Проверка и публикация

Перед публикацией выполните `make -f build/Makefile test` и `make -f build/Makefile site`. Проверьте главную и страницы недель, прямое открытие URL, мобильное меню, работу без JavaScript, клавиатуру и превью. В каталоге проверьте поиск вместе с фильтрами, историю браузера, даты, ссылки, скачивание файлов и просмотр ноутбуков. Материалы без PDF не должны иметь ссылки на PDF; скрытые записи не должны попадать в каталог.

### Проверка в браузере

После `make -f build/Makefile site` запустите локальный HTTP-сервер, как описано выше. В другом терминале выполните:

```bash
mkdir -p output/playwright
npx --yes --package @playwright/cli playwright-cli -s=materials open http://localhost:8000/
npx --yes --package @playwright/cli playwright-cli -s=materials run-code --filename utils/scripts/check-browser.js
```

Нужны Node.js 24 LTS и браузер, поддерживаемый Playwright CLI. Сценарий проверяет текущие две недели, пять материалов, страницу лицензии и соцсети: поиск, фильтры, переход к содержимому, историю, ошибку манифеста, превью с фокусом и наведением, работу без JavaScript. Он делает снимки главной, недель, каталога и лицензии на ширинах 360, 768, 991, 992 и 1440 px с открытым и закрытым меню в светлой и тёмной системной теме; проверяет цвета CS50 и переключение темы без перезагрузки. Результаты остаются в игнорируемом `output/playwright/`. Проверка короткого окна использует размер 1024×400.

Workflow `.github/workflows/presentations.yml` проверяет изменения материалов, интерфейса и окружения на push в `main`/`dev`, а также все PR в эти ветки, включая изменения только документации. Его можно запустить вручную. Push только корневой документации не запускает сборку сайта; PDF на `main` собирается независимо от фильтра путей.

### Окружение и кэш CI

Окружение — Python 3.14 и Node.js 24 LTS, TeX Live, Pandoc, pdfLaTeX, XeLaTeX для логотипа учебников, CM Super, Poppler и CPU PyTorch. Dockerfile и фиксированные версии инструментов находятся в `.github/ci/`; библиотеки примеров — в `handbooks/ml/00-intro/01-environment/requirements.txt`. После изменения зависимостей хеш окружения меняется автоматически. Образ `ghcr.io/beloai/materials/ci:<хеш>` публикуется из `main`/`dev` через `GITHUB_TOKEN` с `packages: write`; организация должна разрешать создание пакетов. PR используют готовый образ либо собирают локальный, без публикации. Buildx восстанавливает слои из кэша GitHub Actions.

CI запускает `npm ci`, `make -f build/Makefile test` и `make -f build/Makefile site` внутри образа. Все ноутбуки проверяются каждый раз: `NOTEBOOK_TEST_WORKERS=2` выполняет два одновременно в отдельных процессах и чистых ядрах; локально по умолчанию используется один процесс. Число внутренних потоков NumPy/PyTorch ограничено в образе.

`.cache/build/` содержит проверяемый по SHA-256 кэш PDF, превью, дополнительных файлов занятий и HTML ноутбуков. Ключи зависят от содержимого исходников, метаданных, общих стилей, сборочных скриптов и окружения, а не от времени файлов. `_site/` очищается и наполняется только актуальными материалами; страницы и манифест генерируются заново. Повреждённые записи пересобираются. Неудачный экспорт не кэшируется. Кэш не входит в артефакт сайта.

`BUILD_CACHE_DIR` задаёт другую папку кэша; `BUILD_CACHE_DISABLE=1 make -f build/Makefile site` полностью отключает чтение и запись. Для очистки удалите `.cache/build/`. Смена версии формата в `build_cache.py` или префикса ключа workflow сбрасывает соответствующий кэш. В summary Actions отображаются время тестов и сборки, попадания в кэш и ссылка на артефакт. Первый запуск холодный; следующие сравнивайте с исходным ориентиром около девяти минут на build.

### Ветки и публикация

Работа ведётся в `dev`, проверенные изменения переносятся PR в `main`. Основной сайт — <https://materials.beloai.by/>, dev — <https://materials.beloai.by/dev/>. Внутренние ветки с открытым PR в `main` или `dev` получают `/test/pr-<номер>/`. Ветки `main`/`dev` не дублируются как PR preview; fork PR только проверяются. Все версии общедоступны; dev и preview получают баннер и `noindex, nofollow`.

Каждая успешная сборка сохраняет `site-<ветка>-<SHA>` или `site-pr-<номер>-<head-SHA>` на 90 дней. PR собирается на merge commit; `build-source.json` связывает его с исходным head SHA и run ID. Publisher проверяет происхождение артефакта и родителя merge commit, не исполняя содержимое архива.

`Publish Pages` работает из default branch после успешных `Presentations`, вручную и после `Preview lifecycle`. Последний обрабатывает закрытие/reopen PR, изменение его base и удаление ветки без checkout или кода PR, затем запускает publisher через `workflow_run`. Это сохраняет ограничение окружения `github-pages` на `main`, в том числе для PR в `dev`.

Каждый publisher заново сверяет существующие ветки и открытые PR. Production размещается в корне, dev — в `/dev/`, preview — в `/test/pr-N/`; эти пути зарезервированы. Закрытие, слияние PR или удаление ветки исключает preview из следующего Pages deploy. Запоздавшая сборка не возвращает удалённую версию. `build-info.json` содержит SHA, run ID, ссылки на сборки, источник и корень каждого окружения.

Общая concurrency-группа `pages-publish` не отменяет текущий deploy. Очередь `single` может заменить ожидающий запуск: полная сверка состояния делает промежуточные события избыточными. Сборки используют отдельные группы по ветке/PR. Перед публикацией проверяются локальные HTML-ссылки и лимит сайта 1 ГБ.

Неудачная новая сборка не заменяет последнюю успешную. Отсутствующий или истёкший артефакт production/dev останавливает публикацию; отсутствие dev допустимо только до его первой публикации. Preview без доступного успешного артефакта пропускается. Для восстановления запустите **Presentations → Run workflow** для main/dev; для PR обновите ветку или повторите его сборку. Затем повторите **Publish Pages**. Исторические артефакты после удаления preview остаются до истечения срока хранения.

В PR появляется нативный GitHub Deployment окружения `preview-pr-N` с кнопкой **View deployment**. Publisher выставляет `in_progress`, а `success` и адрес — только после успешного Pages deploy. При ошибке предыдущая опубликованная версия остаётся активной; после замены или удаления старые deployments переходят в `inactive` (для временного окружения GitHub показывает destroyed). Повторный запуск восстанавливает статусы по опубликованному манифесту; комментарии и labels не создаются. Права publisher: `contents: read`, `actions: read`, `pull-requests: read`, `deployments: write`, `pages: write`, `id-token: write`; используется только `GITHUB_TOKEN`.

Для локальной проверки запустите HTTP-сервер `_pages/`, откройте корень через Playwright CLI и выполните `utils/scripts/check-pages-browser.js`. Сценарий находит окружения по `build-info.json`, проверяет префиксы, файлы, поиск, hash-фильтры, мобильное меню, клавиатуру и работу без JavaScript. Число материалов берётся из манифеста.

Включение: сначала внесите workflows и скрипты в `main`, дождитесь успешной сборки и публикации, затем синхронизируйте существующую `dev` с `main`. Сохраните разрешение окружения `github-pages` только для `main`. Проверьте временный внутренний PR: успешную публикацию, **View deployment**, обновление, закрытие/удаление ветки и 404 по прежнему адресу. Секреты и PAT не требуются.

Не коммитьте `_site/`, `main.pdf`, вспомогательные файлы LaTeX и `node_modules/`. Лицензии описаны в [LICENSE](../../LICENSE).

## Учебник по машинному обучению

ML-хендбук доступен по прямому адресу `/handbooks/ml/`. Текст главной страницы берётся из `handbooks/ml/content.md`, программа — из `handbooks/ml/CURRICULUM.md` и публикуется как `/handbooks/ml/curriculum/`. Отдельных учебников Python и математики больше нет. Не добавляйте черновик в общее меню курса до отдельного решения о выпуске. Страницы и HTML-превью получают `noindex, nofollow`.

`handbooks/handbooks.json` хранит название каталога и ML-хендбук (`handbooks`). В `chapters` перечислены папки глав в порядке чтения. Номер папки не входит в публичный URL: `03-nn-in-practice` публикуется как `/handbooks/ml/nn-in-practice/`.

Глава содержит `README.md` с назначением и оглавлением, `meta.yaml` с метаданными, необязательный `content.md` и пронумерованные папки параграфов. В YAML обязательны `slug`, `title`, `description`, `status` и `paragraphs` (упорядоченный список имён папок). YAML — единственный источник метаданных. Не повторяйте их в общем JSON.

Статусы: `planned`, `draft`, `reviewed`. Авторов запланированной главы можно не указывать. Пустая глава допустима только как `planned`; она не содержит текста и параграфов. Готовая к сборке глава требует `build: true` и текст либо параграфы. Введение — глава `00-intro` с `content.md`; настройка среды — её параграф `01-environment`. Отдельной папки `start` нет.

Для параграфа скопируйте `handbooks/ml/_paragraph-template/` внутрь главы как `01-<slug>`, заполните метаданные и добавьте папку в `paragraphs`. Переведите главу из `planned` в `draft` с `build: true`. Назначение параграфа и правила подготовки находятся в README, текст — в `content.md`, изображения — в `media/`, данные — в `data/`. Ссылки из текста: `media/image.svg`, `data/sample.csv`. Служебные файлы и шаблон не публикуются. Порядок задаётся списком YAML, а не сортировкой папок.

В YAML параграфа обязательны `slug`, `title`, `description`, `status`, `authors`; для текста — `build: true`. `resources` — список объектов `path` и `label` со скачиваемыми файлами. Изображения и данные публикуются автоматически; чтобы добавить ссылку в список файлов, перечислите ресурс явно. Повторные ключи YAML, slug и отсутствующие источники считаются ошибками.

Ноутбук необязателен. Для синхронизации с Python-блоками текста укажите `sync_notebook: true` и ресурс `notebook.ipynb`, затем выполните `python3 utils/scripts/handbook_notebooks.py --write`; `--check` проверяет синхронность. Без этого флага ноутбук сохраняется как самостоятельный исходник. Решения из Markdown при синхронизации выносятся в конец. Инфраструктура выполнения ноутбуков проверяется на синтетических примерах в отдельных ядрах с тайм-аутом и ограничением потоков. Тесты кода не читают реальные учебные материалы.

SVG-рисунки при синхронизации встраиваются в Markdown-ячейки ноутбука, поэтому скачанный ноутбук можно читать отдельно.

HTML-превью используют общий кэш экспорта. Его ключ учитывает ноутбук, локальные метаданные и текст, изображения и данные, сборщик и окружение. Удаление параграфа удаляет его публикацию и совместимые копии при следующей сборке.

Старые ML-адреса `start` и `environment` перенаправляются на `intro`; `diy-nn`, `how-they-learn`, `advanced-math` — на новые главы. Старый префикс `/handbook/` сохраняет переходы и копии актуальных ресурсов. Удалённые уроки ML, Python и математики возвращают 404.

Формулы записывайте как `$…$` и `$$…$$`. KaTeX публикуется локально с лицензией. Пишите собственные тексты; заимствования сопровождайте источником и условиями использования.

Для тестов установите `handbooks/ml/00-intro/01-environment/requirements.txt` и `.github/ci/requirements.txt` в виртуальную среду Python 3.14. В CI используются Node.js 24 LTS и CPU PyTorch. Сборка: `make -f build/Makefile handbooks` или `make -f build/Makefile site`.

После сборки проверьте навигацию и каталог в браузере:

```bash
npx --yes --package @playwright/cli playwright-cli -s=handbook open http://localhost:8000/handbooks/
npx --yes --package @playwright/cli playwright-cli -s=handbook run-code --filename utils/scripts/check-handbook-browser.js
```

Сценарий проверяет навигацию, переходы старых адресов ML, отсутствие удалённых учебников и уроков, файлы, мобильную вёрстку, клавиатуру и работу без JavaScript. Он также работает под префиксом `/dev/`. Содержание учебных текстов тестами не фиксируется.

### Прежние адреса учебников

Канонические страницы находятся в `/handbooks/`. Для известных прежних страниц `/handbook/` сборка создаёт переходы с сохранением query и hash, а для файлов — совместимые копии. Это работает также под `/dev/`. Удалённые ML-уроки не восстанавливаются. Старый каталог совместимости пересоздаётся при каждой сборке.

Тесты кода работают только с временными фикстурами: названия, количество и содержание учебных материалов в них не фиксируются. Браузерный сценарий обходит ссылки опубликованного сайта и проверяет рендеринг, файлы и навигацию без ожидаемого оглавления.

### Авторы материалов

В локальном `meta.yaml` поле `authors` содержит список объектов с `name` и необязательным `role`. Список строк также поддерживается. Для опубликованных глав и параграфов авторы обязательны; пустым запланированным главам авторство не назначается.

```yaml
authors:
  - name: Имя автора
    role: автор исходного материала
  - name: Имя редактора
    role: доработка и обновление
```

Подписи занятий читаются из `course/<вид>/<папка>/meta.yaml` при генерации страниц недель и каталога. Манифест `materials.json` не получает дополнительных полей. Подписи учебника читаются из метаданных глав и параграфов; авторство приветственного текста и программы указано непосредственно в соответствующих Markdown-файлах.

При синхронизации учебного ноутбука авторы передаются генератору из метаданных и попадают в подпись и `metadata.authors`. В самостоятельных ноутбуках занятий подпись хранится в Markdown-ячейке и `metadata.authors`; код ячеек сохраняется. Импортированные PDF/PPTX не переписываются: подпись показывается у ссылки на материал.
